# BandHub · first mobile increment

Expo / React Native / TypeScript client with a Supabase backend migration. The earlier Bandroom web application in `../bandroom` is preserved. This is source code and a locally validated first increment, not a deployed service or an App Store release.

## Implemented

- Account registration, sign-in, email confirmation/reset callbacks and profile text/instruments.
- Private bands, band switching, owner/admin/member permissions and email-bound, expiring invitation links.
- Originals, quick ideas and cover-song metadata; song statuses and idea-to-song conversion.
- Device recording and file upload, append-only recording versions, playback/seek/speed/repeat and timestamp comments.
- Editable lyrics, chords and plain-text guitar tabs, text export, private PDF/text attachments, authorized file downloads.
- Realtime band chat and per-song discussion.
- Known-song metadata search with MusicBrainz and links to lyric/tab providers. No copyrighted lyrics or tabs are scraped or bundled. Upload files you own or are authorized to use; external providers control downloads from their sites.
- A useful setup screen when backend credentials are absent. No sample members or fabricated backend activity.

## Run locally

Install a current Node.js LTS release compatible with Expo SDK 58, then in this directory:

```sh
npm ci
cp .env.example .env
npm start
```

On PowerShell, replace the copy command with `Copy-Item .env.example .env`. Without credentials you can inspect onboarding, setup and song lookup. Authentication and band data require the steps below. Restart Expo after changing environment variables.

Use `npm run web` for a browser preview. Use an Expo Go version supporting SDK 58 for initial phone testing; recording/background behavior and installed deep links must also be tested in a native build. On Windows, Android can run on a connected device or an Android Studio emulator with `npm run android`. Local iOS simulator/native compilation requires macOS and Xcode; use a compatible iPhone client or configure a cloud build from Windows.

## Supabase setup

1. Create your own Supabase project. In its SQL editor, execute `supabase/migrations/202610220001_core.sql`, then `supabase/migrations/202610220002_restrict_anonymous_function_execution.sql`, once in that order against a new project. It is transactional and creates tables, policies, functions, the private bucket and Realtime table publication entries. For a project with existing tables, review conflicts before applying. This migration is not a repeatable seed script.
2. Copy the project URL and **publishable key** into `.env`:

   ```dotenv
   EXPO_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
   EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
   ```

   A legacy anon key is supported. Never put a service-role key in the app. These public client variables are bundled into the app; authorization is enforced by database and storage policies.
3. Enable email/password authentication and email confirmations. Configure email delivery for real users in Supabase. Configure Auth URL redirects for `bandhub://auth/callback` in installed builds and your exact web origin followed by `/auth/callback`. For Expo Go, add the actual development callback URL generated by Expo Linking for your device/server; development URLs differ from installed-app URLs. Password reset and confirmation links must return to the same app environment where they will be used.
4. Check Storage: the `band-files` bucket must be **private**. The migration limits uploads to 25 MB and the listed audio/PDF/text MIME types. Do not add public read/write policies. Paths contain band, uploader and song IDs. Downloads use short-lived signed URLs (60 seconds); an issued URL can remain valid until it expires after a member is removed.
5. Confirm the `supabase_realtime` publication contains the tables listed at the end of the migration. If Realtime was unavailable when the migration ran, enable those tables in the dashboard. Chat also provides manual refresh.
6. Restart the app, register and confirm an account, create a band, then invite a second confirmed account using its email. Share the generated invitation link yourself; the app does not send invitation email. The recipient must sign in with the matching confirmed email, then reopen or paste the invitation link. Invitation tokens expire after seven days and can be used once.

## Data and authorization

`profiles` holds musician information; `bands` and `memberships` define access. `invitations` stores hashed tokens. `songs` stores originals, ideas and covers plus editable text; `recordings` stores immutable versions; `documents` stores private attachment metadata; `messages` and `comments` store discussions and timestamp annotations.

Band creation, invitations, role changes and recording finalization use restricted database functions. RLS isolates bands; composite foreign keys prevent cross-band song/file/comment references. Upload metadata failures attempt to remove the orphan file. Native auth tokens use chunked SecureStore storage. Browser sessions use browser persistence, so use trusted devices.

## Tests and builds

```sh
npm test
npm run typecheck
node --import tsx --experimental-test-coverage --test tests/*.test.ts
npm run export
```

The SQL tests run the actual migration in embedded PostgreSQL with simulated Supabase auth/storage schemas and distinct authenticated users. They do not connect to or modify a hosted project. See `docs/tdd-evidence.md` for evidence and coverage scope.

For native distribution, choose bundle/package identifiers you own in `app.json`, configure your Expo/EAS project and signing credentials, and provide the same public environment variables to your build environment. With EAS CLI configured, `eas build --platform android --profile preview` produces an internal Android build; use the production profile for release builds. iOS requires Apple signing/provisioning. Cloud builds and store accounts may have costs: no cloud build or paid resource has been created. `expo export` produces JavaScript/assets, not an APK/IPA.

## Known limitations and next increment

The BandHub Supabase schema has been deployed; see docs/supabase-deployment.md. Hosted auth, email delivery, file transfer and two-user Realtime behavior have not been verified. Physical microphone permissions, background audio, sharing and native deep links still need Android/iOS testing. Online provider availability and browser CORS can affect metadata search; source links remain available.

The source now includes a band calendar, external venue search and recording a separate instrument take over a looping guide. These are not in the 0.1.0 APK; see docs/collaboration-update.md. Availability voting, setlists, tasks, in-app venue listings, profile photos, push notifications, rich musical notation and licensed lyric/tab download integrations remain pending. Role enforcement and removal exist in SQL, but a full membership administration interface is still pending. Saved text requires an explicit save; navigating away or closing the app can discard unsaved text or an unuploaded recording. Downloads may remain in the device cache. Offline synchronization and concurrent text-edit conflict handling are not implemented. File type validation is metadata-based, not malware/content scanning.

Next: create/configure Supabase using this guide, complete a two-account device acceptance run, then address editing/recording interruption recovery and membership administration before adding rehearsal scheduling.

Architecture rationale: `docs/architecture.md`. Source: `app/` routes and `src/` services/components. Tests: `tests/`. No data from the prior web app is automatically migrated; that needs an explicit ownership mapping.
